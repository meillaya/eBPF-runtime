# Recorder benchmark methodology (0.3)

Status: harness added; numbers are recorded only from real root runs, never
projected. Run the harness on the target host and publish its JSON.

## What is measured

`scripts/bench/run.sh` runs `ebpf-fleet record` for a fixed duration under a
deterministic process/file/mixed workload and records:

- wall time, user/system CPU time, and CPU percent of the recorder;
- maximum RSS;
- events recorded, events/second;
- bundle size;
- average of five `select count(*)` query latencies.

It uses a static or release `ebpf-fleet` binary and writes artifacts under
`target/bench/<UTC stamp>/`. It does **not** yet compare against `bpftrace`
or `perf`; add a separate comparison script/result before making a
comparative claim.

## Commands

```bash
sudo scripts/bench/run.sh --duration 10 --workload mixed --stacks off
sudo scripts/bench/run.sh --duration 10 --workload process --stacks events
```

The harness must run as root because BPF loading needs CAP_BPF/CAP_PERFMON.
For VM runs, copy the static binary into the guest and run the same command.

## Interpretation

- CPU percent is recorder CPU time divided by wall time. With a saturated
  single workload, values near 100% mean one core; multi-core host totals
  need context.
- Event loss is not yet inferred from workload counts; the recorder's
  `--stats`/drop counters are the authoritative loss source once available.
- Query latency includes cold process startup per query; it is a daily CLI
  latency, not a long-lived server latency.
- Publish host kernel, CPU, workload, binary hash, and exact command with
  every result. Do not compare numbers across different workloads.

## Results

### 0.2.2 baseline (KVM functional environment)

This is a **single-run baseline**, not a bare-metal release SLO and not a
comparison with `perf`/`bpftrace`. It exercises the harness end to end.

- Guest: Ubuntu 24.04.5 LTS, kernel `6.8.0-147-generic`, 4 vCPU KVM guest on
  the `massive` host (AMD Ryzen 7 5700X, 16 host CPUs).
- Binary: released static `ebpf-fleet 0.2.2`, sha256
  `a4e158d4e0ab9c0162ab7f0ca5e24d581052a5edb2736c4d273f326efe5f1243`.
- Workloads: `process`, `file`, and `mixed` for 5 seconds each, `--stacks off`.
- Raw JSON: [process](0.2.2-ubuntu-24.04-process.json),
  [file](0.2.2-ubuntu-24.04-file.json), [mixed](0.2.2-ubuntu-24.04-mixed.json).

| Workload | Events | Events/s | Recorder CPU | Max RSS | Bundle | Query avg |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| process | 34,581 | 5,676 | 8.04% | 27,708 KB | 20.8 MB | 36.7 ms |
| file | 53,552 | 8,619 | 13.52% | 27,708 KB | 33.3 MB | 63.7 ms |
| mixed | 57,768 | 9,438 | 11.11% | 27,672 KB | 35.7 MB | 51.7 ms |

The workload generator itself consumes CPU and its event rate is not a
controlled kernel load; treat these numbers as harness validation and a
starting point. Replace with a bare-metal, pinned-CPU run and add
`perf`/`bpftrace` comparison before using them for adoption claims.

### 0.3.0 stack-mode overhead (KVM functional environment)

Same guest and 5-second `mixed` workload, **published** static
`ebpf-fleet 0.3.0` asset
(`sha256 97a29a234e5279735b47eface8ef58b484cf0d5d4e68a012da56af1969a37385`).
Raw JSON: [off](0.3.0-release-stacks-off.json),
[events](0.3.0-release-stacks-events.json),
[all](0.3.0-release-stacks-all.json).

| Stack mode | Events | Events/s | Recorder CPU | Max RSS | Bundle | Query avg |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 62,457 | 10,174 | 10.43% | 29,092 KB | 38.6 MB | 53.8 ms |
| events (default) | 60,764 | 9,859 | 26.77% | 69,824 KB | 40.4 MB | 54.7 ms |
| all | 68,087 | 11,122 | 26.30% | 72,644 KB | 45.4 MB | 60.2 ms |

Takeaways, with caveats:

- Stack capture roughly **2.6×** the recorder CPU and RSS of `off` in this
  short, high-churn workload; most of the cost is symbolization and the
  10k–12k distinct stacks the workload creates.
- Events/s is workload-generator dependent and not a fixed-rate load; the
  `off` run is not a throughput claim and the `events`/`all` event counts
  vary with scheduler timing. Compare CPU/RSS/bundle/query, not event rate
  alone.
- `--stacks off` is the right default for latency-sensitive production
  captures until a lower-overhead sampling/batch mode exists. The 0.3
  default is `events` because incident debugging is the primary local use
  case; this is a policy decision to revisit after a controlled benchmark.
