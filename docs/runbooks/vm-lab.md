# Local VM lab (KVM and TCG)

Disposable cloud-image VMs on a Linux host. Native boots use KVM; a
cross-architecture image can be booted with QEMU TCG system emulation for
a functional smoke only. The lab runs its kernel-matrix and rootful
data-path work on this machine ("massive") in local KVM VMs: no dependency
on `machine0`, no host root, no libvirt, no host bridges and no rootful
host Podman.

The lab is intentionally small: one Bash entry point, one JSON image
catalogue, one full cloud-init template plus a lean variant for emulated
boots. VMs are recreated from a pinned base image on demand, and every
generated byte stays under `target/vm/`.

## Host prerequisites

| Requirement | Check | This host |
| --- | --- | --- |
| Linux KVM host | `ls -l /dev/kvm` | `crw-rw-rw- root:kvm`, usable without sudo (needed for native KVM boots only) |
| QEMU system emulator | `qemu-system-x86_64 --version` / `qemu-system-aarch64 --version` | QEMU 10.2.2 from the devenv shell (both binaries) |
| AArch64 UEFI firmware | `--firmware` / `VM_ARM64_UEFI` | `target/vm/firmware/AAVMF_CODE.fd` (see below) |
| Image + seed tools | `command -v qemu-img cloud-localds xorriso` | provided by the devenv shell |
| SSH client | `command -v ssh ssh-keygen` | provided by the devenv shell |
| JSON/locking tools | `command -v jq flock` | provided by the devenv shell |
| Disk headroom | `df -h target/vm` | ~600 MiB per pinned image + sparse 20 GiB overlays |
| Network for bootstrap | HTTPS to the vendor image host | outbound HTTPS works; the guest also gets internet through user-mode NAT |

What the lab never does: it does not call `sudo`, does not use `libvirt`,
host systemd units, bridges, taps, iptables, or rootful host Podman. A
native KVM boot only needs read/write access to `/dev/kvm`; a
cross-architecture boot uses the unprivileged TCG accelerator instead and
needs no `/dev/kvm` at all.

## Enter the toolchain

`devenv.nix` adds `qemu`, `cloud-utils` (for `cloud-localds`), `openssh`,
`jq` and `xorriso` to the developer shell. Run the lab from inside it:

```bash
devenv shell
qemu-system-x86_64 --version
command -v cloud-localds xorriso
```

If you are on a bare Nix host without the devenv shell, point the lab at
the tool directories (the same escape hatch used by
[the rootful runbook](rootful-compose.md)); `xorriso` is a complete
fallback for `cloud-localds`, so only the QEMU and ISO tool directories
are strictly needed:

```bash
export VM_LAB_TOOL_PATH="$(ls -d /nix/store/*-qemu-*/bin | tail -1):$(ls -d /nix/store/*-libisoburn-*/bin | tail -1)"
scripts/vm/lab.sh status
```

The lab fails closed with an actionable message when the qemu binary,
`/dev/kvm` (for a KVM boot), the AArch64 UEFI firmware, `qemu-img`, the
seed writer or SSH is missing. A native image is always booted with KVM; a
cross-architecture image is booted with TCG and every log/line/evidence
file says so ("functional smoke only, not performance").

## Quick start

```bash
# 1. verify/create target/vm layout, download + verify the pinned image,
#    generate the ephemeral SSH key. No VM is booted.
scripts/vm/lab.sh bootstrap

# 2. boot the default image as instance ubuntu-24-04
scripts/vm/lab.sh up

# 3. inspect it
scripts/vm/lab.sh status
scripts/vm/lab.sh run --name ubuntu-24-04 -- uname -r
scripts/vm/lab.sh ssh --name ubuntu-24-04

# 4. stop it and delete the overlay
scripts/vm/lab.sh down --name ubuntu-24-04
```

The one-shot smoke test boots a VM, runs the checks, and tears it down:

```bash
scripts/vm/run-smoke.sh              # boot, 4 checks, teardown
scripts/vm/run-smoke.sh --keep       # leave the VM running for debugging
```

## Commands

| Command | Purpose |
| --- | --- |
| `bootstrap` | Create `target/vm/` layout, verify/download the pinned base image, generate the ephemeral SSH key. No VM boot. |
| `up` | Create a qcow2 overlay and a cloud-init NoCloud seed, boot QEMU (KVM for a native image, TCG for a cross-architecture image), wait for SSH. |
| `run` | Run a command in a running instance over SSH; arguments after `--` are the guest command. Exit status is propagated. |
| `ssh` | Interactive SSH shell into an instance (or a remote command after `--`). |
| `down` | Stop an instance and remove its overlay/seed; `--all` stops every instance and any orphan QEMU process for this lab root; `--purge` removes the instance directory too. |
| `status` | Base images with size/date, instances with running/stale/stopped state, PID, SSH port, image, guest arch and accelerator, plus orphan QEMU detection. |
| `collect` | Copy per-instance QEMU/console logs and, when running, guest diagnostics (`uname`, `os-release`, `cloud-init status`, BTF, sudo, dmesg, network) under `target/vm/collected/<UTC timestamp>/`. `--all` collects every instance. |
| `copy` | Stream one file between the host and a running VM over the same SSH path `run` uses (no scp/sftp, no extra guest packages): `copy --name <n> <local> <guest-path>` uploads, `copy --name <n> --from-guest <guest-path> <local>` downloads. The transfer is size-checked and fails closed. |

Common options (all commands): `--image <name>` (image key from
`scripts/vm/images.json`), `--name <instance>` (default: the image key
with dots replaced by hyphens), `--port`, `--cpus`, `--memory`,
`--disk-size`, `--timeout`, `--accel <auto|kvm|tcg>`, `--help`. `copy`
adds `--from-guest` to reverse the transfer direction. `bootstrap` also
accepts `--all-images` (every pinned image for the host architecture) and
`--force` (redownload the cached base image). `down` and `collect`
accept `--all`; `down` additionally accepts `--purge`.

Acceleration selection: `--accel auto` (the default) uses KVM when the
image architecture matches `uname -m` and TCG when it does not. `--accel
kvm` on a cross-architecture image is a hard error (KVM cannot boot a
foreign guest); `--accel tcg` forces emulation, including for a native
image (debugging only). An emulated boot prints a TCG warning and records
`emulated: true` plus the accelerator in `instance.json`; that row is a
functional smoke, never a performance number.

AArch64 guests boot through AArch64 UEFI firmware (AAVMF/QEMU_EFI); there
is no direct kernel boot for the Ubuntu arm64 cloud image. Resolve it in
this order: `--firmware <path>`, `VM_ARM64_UEFI`, then
`target/vm/firmware/AAVMF_CODE.fd`, then the distro paths
`/usr/share/AAVMF/AAVMF_CODE.fd`, `/usr/share/edk2/aarch64/QEMU_EFI.fd`
and friends. The lab never downloads firmware. On Debian/Ubuntu install
`qemu-efi-aarch64` and use `/usr/share/AAVMF/AAVMF_CODE.fd`; on a host
without that package, fetch the `qemu-efi-aarch64` `.deb` and extract
`usr/share/AAVMF/AAVMF_CODE.fd`:

```bash
mkdir -p target/vm/firmware target/vm/tmp
curl -fL -o target/vm/tmp/qemu-efi-aarch64.deb \
  http://ports.ubuntu.com/ubuntu-ports/pool/main/e/edk2/qemu-efi-aarch64_2024.02-2_all.deb
(cd target/vm/tmp && ar x qemu-efi-aarch64.deb &&
  tar --zstd -xf data.tar.zst ./usr/share/AAVMF/AAVMF_CODE.no-secboot.fd)
cp target/vm/tmp/usr/share/AAVMF/AAVMF_CODE.no-secboot.fd \
  target/vm/firmware/AAVMF_CODE.fd
```

`--cloud-init full|lean` chooses the seed profile. `full` (default) is
`scripts/vm/cloud-init/user-data.tmpl` and installs `curl`, `jq` and
`ca-certificates`; `lean` is `user-data-lean.tmpl`, skips apt, and only
creates the `fleet` user/key. The arm64 TCG row uses `lean` because an
emulated apt run costs many minutes and the binary under test is static.

Environment overrides: `VM_LAB_ROOT`, `VM_LAB_TOOL_PATH`, `VM_ACCEL`,
`VM_ARM64_UEFI`, `VM_CLOUD_INIT`, `VM_CPUS`, `VM_MEMORY_MB`,
`VM_BOOT_TIMEOUT`, `VM_PORT_BASE`, `VM_PORT_MAX`.

Examples:

```bash
scripts/vm/lab.sh up --image ubuntu-24.04 --name lab-noble --cpus 4 --memory 4096
scripts/vm/lab.sh run --name lab-noble -- 'uname -r; ls -l /sys/kernel/btf/vmlinux'
scripts/vm/lab.sh collect --name lab-noble
scripts/vm/lab.sh down --all
```

## What a boot does

1. `bootstrap`/`up` verify the cached base image against the pinned
   sha256 in `scripts/vm/images.json`; a missing or unpinned entry fails
   closed before any download.
2. `up` creates `target/vm/instances/<name>/overlay.qcow2`, a qcow2
   overlay backed by the read-only base image.
3. The cloud-init templates in `scripts/vm/cloud-init/` are rendered into
   `instances/<name>/seed/` with the ephemeral public key and an
   instance-id, then packed into `seed.iso` with `cloud-localds`
   (fallback: `xorriso`/`genisoimage`, volume label `cidata`).
4. QEMU starts with a virtio disk and NIC, a virtio RNG, `-display
   none`, a serial console log, and user-mode networking whose only
   inbound path is `tcp:127.0.0.1:<port>-:22`. A native image uses
   `-accel kvm -cpu host` and the x86_64 device model validated by the
   kernel matrix; an aarch64 image uses `-machine virt -cpu max -bios
   <AAVMF_CODE.fd>` and virtio-blk for both the overlay and the NoCloud
   seed, with `-accel tcg,thread=multi` when emulated.
5. The instance metadata (`instance.json`: image, port, pid, paths) is
   written before the SSH wait begins, so `status`/`down` can always find
   the instance even if boot hangs.
6. `up` waits for SSH as user `fleet`; on timeout it stops the VM and
   prints the tail of the console and QEMU logs.

Guest contract from cloud-init: user `fleet` with the generated key and
passwordless sudo inside the guest. The full seed also installs `curl`,
`jq` and `ca-certificates`; the lean seed installs no packages at all.
The guest's `fleet` account is a throwaway test identity; the SSH key is
generated per workspace under `target/vm/keys/` and only authorizes this
guest.

## Write containment

Everything the lab creates is below `target/vm/`, which `target/` rules
already gitignore:

```
target/vm/
  lock                       # flock file serializing setup/teardown
  images/                    # verified base cloud images (read-only use)
  firmware/                  # AArch64 UEFI firmware for arm64 TCG boots
  arm64/<stamp>/             # run-arm64.sh functional-row evidence
  tmp/                       # resumable downloads (.partial files)
  keys/                      # ephemeral SSH keypair (mode 0700)
  logs/lab.log               # lab-level event log (up/down/download)
  instances/<name>/
    instance.json            # image, port, pid, paths, timestamps
    overlay.qcow2            # discarded on down
    seed.iso, seed/          # cloud-init NoCloud seed
    qemu.pid
    logs/console.log         # guest serial console
    logs/qemu.log            # QEMU error log
  collected/<timestamp>/     # `collect` output
```

Nothing is written to `/etc`, `/var`, `/run`, the user's home directory,
or any other host path. The SSH client is invoked with
`UserKnownHostsFile=/dev/null` and `StrictHostKeyChecking=no`, so it never
writes a `known_hosts` entry. QEMU user-mode networking owns its own
internal NAT inside the process; the lab creates no host interfaces or
firewall rules.

Reset everything with `scripts/vm/lab.sh down --all && rm -rf target/vm`.

## Networking

- The only host listener is QEMU's `hostfwd` on `127.0.0.1:<port>` to
  guest port 22. Ports are allocated from `2222-2299` and recorded in
  `instance.json`; use `--port` to pin one.
- The guest sees QEMU's slirp network (`10.0.2.15/24`, gateway
  `10.0.2.2`, DNS `10.0.2.3`) and reaches the internet outbound; there is
  no inbound path other than the SSH forward.
- Several instances can run at once, each with its own SSH port. `flock`
  serializes image/overlay/seed setup and teardown so two commands cannot
  race the same instance directory.

## Image pins

`scripts/vm/images.json` is the single source of truth for base images.
The default (`ubuntu-24.04`) is pinned to an immutable dated Ubuntu build
URL and its SHA-256, cross-checked against the vendor `SHA256SUMS`
manifest. The verification policy is fail-closed: an entry with a null
`sha256` or non-`pinned` status is never downloaded; the script prints the
URL, checksum manifest and pin instructions instead.

The kernel-matrix entries are placeholders until their hashes are pinned
and boot-validated:

| Image key | Distro / kernel series | Status |
| --- | --- | --- |
| `ubuntu-24.04` | Ubuntu 24.04 (noble), 6.8 | pinned, default |
| `ubuntu-22.04` | Ubuntu 22.04 (jammy), 5.15 | hash pinned, not yet boot-validated |
| `debian-12` | Debian 12 (bookworm), 6.1 | placeholder (Debian publishes SHA-512 manifests) |
| `debian-13` | Debian 13 (trixie), 6.12 | placeholder |
| `fedora-42` | Fedora 42, 6.14 | placeholder (Fedora 42 is past upstream support; archived mirrors) |
| `ubuntu-24.04-arm64` | Ubuntu 24.04 (noble) on aarch64 | pinned and boot-validated under QEMU TCG (functional only; no native aarch64 KVM host) |

Pin procedure (also encoded in `verification.pin_steps` in the JSON):

1. Pick an immutable vendor build directory. For Ubuntu use
   `https://cloud-images.ubuntu.com/releases/<release>/release-<YYYYMMDD>/`;
   do not pin the moving `release/` or `current/` paths.
2. Read the vendor checksum manifest next to the image and copy the hash
   for the exact file name.
3. Download the image over HTTPS, verify it against the manifest
   (`sha256sum -c` for Ubuntu/Fedora, `sha512sum -c` for Debian), and
   record `sha256sum` of the verified file in `images.json`.
4. Set `status: "pinned"` and run
   `scripts/vm/lab.sh bootstrap --image <name>`; the cached file is
   re-verified on every `up`.
5. Boot it (`up`/`run-smoke.sh`) and only then set `boot_validated: true`.

`bootstrap --all-images` fetches every `pinned` image whose `arch`
matches the host, so an x86_64 host does not download the arm64 entry.
`bootstrap --image ubuntu-24.04-arm64` fetches it explicitly; that is the
first step of the TCG functional row below.

## Kernel matrix

The kernel matrix runs the same static `target/release/ebpf-fleet` binary on
pinned guest kernels and writes machine-readable evidence. The runner is
`scripts/vm/run-matrix.sh`; for every image it boots a VM, copies the static
binary in over `lab.sh copy`, verifies the guest sha256, runs
`doctor --json`, `record --for 8` with deterministic process/file activity,
`query` for kind counts and `FileOpen` paths, `replay`, a process-only probe
record (to check the fork/exec/exit tracepoint path), exports the
bundle, writes a per-row JSON file and tears the VM down even on failure.

```bash
# Run the pinned rows (each image boots once, results under target/vm/matrix/):
nix develop --impure --command scripts/vm/run-matrix.sh \
  --image ubuntu-24.04 --image ubuntu-22.04

# Every pinned image matching the host architecture:
nix develop --impure --command scripts/vm/run-matrix.sh --all-pinned

# Add a Debian/Fedora/arm64 row once its image is pinned in images.json:
nix develop --impure --command scripts/vm/run-matrix.sh --image debian-12
```

The runner is fail-closed: unpinned images, a non-static binary, a failed
boot, a failed record/query/replay, a missing `FileOpen` path or an
unexpected kernel series fail the run instead of skipping a row. Evidence:

```
target/vm/matrix/<stamp>/
  matrix-summary.json          row table, host facts, pass/fail counts
  <image>.json                 kernel release, BTF sha256, sensor results,
                               counts, replay first line, per-check results
  <image>/                     raw artifacts: doctor.json, record stderr,
                               query tables, replay.jsonl, exported bundle,
                               guest facts ([bundle], [btf], [security], ...),
                               console/qemu logs
```

The live results (exact kernel releases, image sha256 values, pass/fail) are
recorded in
[docs/verification/kernel-matrix.md](../verification/kernel-matrix.md).
Current matrix result: 5/5 pinned x86_64 rows PASS (Ubuntu 24.04/22.04,
Debian 12/13, Fedora 42), including `ProcessExit` events via
`tracepoint/sched/sched_process_exit`. The arm64 row is not part of the
KVM matrix on this host (no native aarch64 KVM); it runs through the TCG
functional runner described in the next section and is never mixed into
the performance/kernel matrix rows.

The rest of the old expansion path still applies to new images:

- Debian and Fedora cloud images also understand the NoCloud datasource;
  the `fleet` user is created by the same template. Their default users
  (`debian`, `fedora`) remain unused.
- Package installation on first boot (`package_update: true`) can still be
  running after SSH is ready; the matrix runner polls for
  `cloud-init status` `done` plus `jq`/`tar`/passwordless sudo before it
  records, and the manual equivalent is
  `lab.sh run --name <name> -- 'cloud-init status --wait'`.
- On a native aarch64 KVM host, `--image ubuntu-24.04-arm64` boots the
  pinned arm64 build with the same matrix commands (`run-matrix.sh` only
  accepts images matching the host architecture). On this x86_64 host the
  equivalent functional proof is `scripts/vm/run-arm64.sh` under TCG.
- Host-size guidance: 16 CPUs / ~62 GiB RAM supports several 2-4 GiB
  guests at once; each guest needs its own SSH port and instance name, and
  only setup/teardown is serialized by `flock`.

## arm64 build and TCG functional row

There is no native aarch64 KVM host on this machine, so the 0.3 arm64
evidence has two parts: a real cross-build of the static binary for
`aarch64`, and a functional smoke on a real aarch64 guest kernel booted
with QEMU TCG. The guest is a genuine arm64 Ubuntu kernel (all BPF
verifier/attach/CO-RE work happens inside the guest), but the CPU is
emulated: the row proves functional correctness only and makes no
performance claim.

Build the binary (cross toolchain from the pinned flake inputs; the
sensors need an arm64 kernel BTF because `bpf-build` always compiles CO-RE
objects against `/sys/kernel/btf/vmlinux`):

```bash
nix develop --impure --command bash -c '
  scripts/build-static.sh --arch aarch64 --btf target/cross/arm64-vmlinux.btf'
# -> target/release/ebpf-fleet-aarch64 (+ .sha256)
```

The BTF is the exact blob the pinned guest kernel exposes, so the cross
build compiles the same arm64 type layout a native aarch64 build would.
The script bind-mounts it read-only over `/sys/kernel/btf/vmlinux` inside
an unprivileged user+mount namespace, then verifies ELF machine
`AArch64`, static linkage, no `NEEDED` entries and no `PT_INTERP`
before writing the asset. Get the BTF from the guest with the lab:

```bash
mkdir -p target/cross
scripts/vm/lab.sh up --image ubuntu-24.04-arm64 --cloud-init lean \
  --accel tcg --name arm64-tcg
scripts/vm/lab.sh copy --name arm64-tcg --from-guest \
  /sys/kernel/btf/vmlinux target/cross/arm64-vmlinux.btf
```

Then run the whole row (boots a fresh TCG guest, copies the binary,
verifies the guest sha256, runs `--version`, `doctor --json`, `record`,
`query`, `replay`, writes evidence, tears down unless `--keep`):

```bash
nix develop --impure --command scripts/vm/run-arm64.sh
# -> target/vm/arm64/<stamp>/row.json and row.txt
```

The runner is fail-closed: an unpinned/foreign image, a non-AArch64 or
non-static binary, a failed boot or cloud-init, a failed `doctor`, a
record with zero events, a `FileOpen` path that was not decoded, or a
replay line count that does not match the recorded event count fails the
row (exit 1). Results and the exact TCG caveat are recorded in
[docs/verification/arm64.md](../verification/arm64.md).

## Troubleshooting

| Symptom | What to do |
| --- | --- |
| `error: /dev/kvm is missing` | A native (same-arch) boot needs KVM; check firmware settings and `lsmod | grep kvm`. A cross-architecture image can still boot with `--accel tcg` without `/dev/kvm`. |
| `missing required tools: qemu-system-x86_64 ...` / `qemu-system-aarch64` | Run inside `devenv shell`, or set `VM_LAB_TOOL_PATH` as above. |
| `an aarch64 image needs AArch64 UEFI firmware (AAVMF)` | Put `AAVMF_CODE.fd` in `target/vm/firmware/`, pass `--firmware`, or set `VM_ARM64_UEFI`; see the firmware extraction snippet above. |
| `no cloud-init NoCloud seed writer found` | `cloud-localds` (cloud-utils) is missing and no `xorriso`/`genisoimage` fallback is on PATH; use the devenv shell. |
| `sha256 mismatch` | The download was corrupted or the pin moved. Re-run `bootstrap`; if it repeats, re-pin from the vendor checksum manifest. |
| `SSH did not become ready within Ns` | Inspect the tail printed by `up`, then `target/vm/instances/<name>/logs/console.log` and `logs/qemu.log`, or `lab.sh collect`. Under TCG a first boot can take several minutes; raise `--timeout` (the arm64 runner defaults to 900 s). Common causes: cloud-init seed not attached, missing/wrong UEFI firmware, image arch mismatch, memory too low. |
| `port ... already in use` | Pass `--port`, or free the recorded instance with `down`. |
| `instance ... already running` | Use `lab.sh status`, then `down --name <name>` before booting that name again. |
| Guest has no internet | Check `run -- ip -br addr` and `run -- cat /etc/resolv.conf`; slirp provides `10.0.2.3` DNS. Corporate proxies need guest-side configuration. |
| cloud-init issues | `lab.sh run --name <name> -- 'cloud-init status --long'` and read `/var/log/cloud-init-output.log` inside the guest. |
| Stale state after a crash | `lab.sh status` shows stale PIDs and orphan QEMU processes; `down --all` cleans them up; `down --all --purge` removes instance directories. |

The guest console log is the first place to look for a boot failure; it
is always kept under `target/vm/instances/<name>/logs/console.log` even
when a boot times out.
