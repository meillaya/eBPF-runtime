# ebpf-runtime-security-observability - Work Plan

## Scope
### Must have
- A greenfield Git/Cargo workspace with `devenv.yaml`, `devenv.nix`, `devenv.lock`, `flake.nix`, `flake.lock`, pinned Rust/Clang/LLVM/libbpf/bpftool/Bun tooling, deterministic code generation, quality/supply-chain checks, and separate deterministic versus privileged CI lanes.
- C/libbpf CO-RE sensors and a versioned C→Rust event ABI for process fork/exec/exit; enumerated file open/write-intent/create/unlink/rename coverage; connect/accept/state changes; bounded DNS packets; configured syscall-latency histograms; credential, cgroup, and namespace facts; and explicitly supported BPF LSM audit/deny hooks.
- Semantic honesty in every API and UI: distinguish `ATTEMPT`, `RESULT`, `ESTABLISHED`, `DNS_PACKET`, `OWN_LSM_DENY`, `NO_RETURN`, `ORPHAN_ENTER`, and `ORPHAN_EXIT`; attach validity/degradation/truncation/redaction flags; never strengthen a narrower hook into a generic claim.
- Actual compatibility negotiation on Linux 5.15, 6.1, 6.6, and current, x86_64 and arm64, including readable compatible BTF, hook/field presence, classic TC versus TCX, cgroup v1/v2, active BPF LSM, privileges, and named degraded coverage.
- Shared ring-buffer ingestion with independently polled monotonic attempt/drop counters, bounded Rust channels, visible sequence gaps, explicit outbox/Kafka/ClickHouse lag, and a supported-load envelope under which critical synthetic events have zero observed loss.
- A Rust node agent with safe ABI decoding, process/socket/DNS correlation, CRI/containerd/CRI-O/Docker and Kubernetes enrichment, privacy/redaction before persistence, SQLCipher-v4-compatible local history/outbox, Prometheus metrics without high-cardinality labels, structured logs, health/readiness, and standalone REST/WebSocket/CLI operation.
- A versioned JSON-Schema-backed YAML rule DSL with typed fields, lists, exceptions, bounded predicates, temporal sequences, severities/tags, fixtures, and default sensitive-file, reverse-shell, and container-escape indicator packs.
- Audit-only-by-default eBPF LSM enforcement limited to file access, binary execution, and socket connection; two-phase `STAGE → READY → COMMIT → APPLIED` activation; replay/stale rejection; last-known-good offline state; non-pinned deny links; prior BPF-program return preservation; own-denial attribution only; and an immediate fail-open kill switch.
- A full fleet path with SPIFFE/SPIRE Workload API identity and SVID rotation, separate deadline-bound gRPC control/event streams, deterministic event/batch identities, Kafka durable acceptance before agent ACK, PostgreSQL authoritative control state and same-transaction append-only audit, ClickHouse at-least-once ingestion with explicit dedup/DLQ, OIDC authorization-code+PKCE and device flow, and server-side RBAC.
- A Rust CLI and a purpose-built React/TypeScript/Vite dashboard for live/historical process trees, sockets, DNS packets, file events, syscall histograms, alerts, agents, drops, rules, and policy rollout; authenticated fleet mode and loopback-only no-auth development mode.
- Root-owned systemd delivery, standalone Docker/Compose, verified amd64/arm64 OCI indexes, a Helm v2 chart with capability-minimized DaemonSet and control-plane Deployments, external SPIRE/OIDC/PostgreSQL/Kafka/ClickHouse integration values, upgrades/rollbacks, SBOM/provenance, and an explicitly separate privileged compatibility profile.
- Contract-first unit/property/fuzz tests; privileged sensor/enforcement/compatibility tests; Docker/CRI/Kubernetes attribution tests; fleet auth/protocol/durability tests; browser/visual/accessibility tests; and fair no-agent/observe/enforce/strace/auditd/Falco benchmark runs with raw evidence and a strict p99-and-throughput sub-5% release gate.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No Windows/macOS sensor, kernel module, custom kernel patch, runtime compilation on target nodes, support below Linux 5.15, or sensor startup without readable compatible BTF.
- No arbitrary packet capture, encrypted/plaintext payload interception, command output, keystroke capture, environment capture by default, unbounded argv, or persistence/export before configured redaction.
- No generic “complete file access,” “DNS lookup,” “all syscall latency,” “lossless,” “exactly once,” or “final LSM denial” claim that the underlying hook/pipeline cannot prove.
- No default-on/default-deny enforcement, heuristic-only deny, pinned enforcement link, silent fail-closed behavior, remote shell/command execution, or claim that this replaces SELinux/AppArmor/seccomp/network policy.
- No Falco-syntax compatibility promise, general-purpose policy language, user-supplied arbitrary kernel hook, kernel-side dynamic expression compiler, machine-learning anomaly detection, or remediation outside the approved LSM deny surface.
- No bespoke CA, OIDC provider, database, broker, ClickHouse cluster, consensus algorithm, Kubernetes distribution, or container runtime; production integrations remain external.
- No direct agent database/broker/ClickHouse credentials, direct browser-to-agent privileged RPC, unauthenticated non-loopback listener, static production tokens, or database RLS as the primary authorization boundary.
- No silent duplicate removal, unknown-attribution guessing, historical row rewriting, invisible event loss, or deployment image referenced by mutable tag alone.
- No `procMount: Unmasked`, default full-privileged DaemonSet, `hostPID: true` without evidenced need, or pinned deny links that outlive the loader.
- No multi-region active-active DR, SaaS tenant billing/administration, adversarial multi-tenant isolation promise, or guest-process visibility claim for VM-isolated runtimes such as Kata/gVisor.
- No module over 250 pure LOC without decomposition, no `unwrap`/`panic`/`any` in production code, no unbounded channel/map/cache, and no tests that pass from grep-only evidence or worker self-report.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: **Contract-first TDD**. Rust: `cargo nextest`, `cargo test`, `proptest`, `cargo-fuzz`, Miri for ABI parser/unsafe boundaries, Clippy and rustfmt. C/eBPF: Clang warnings-as-errors, static assertions, `bpftool gen skeleton`, verifier load/attach tests, kernel selftest-style fixtures. TypeScript: Bun, Biome, `tsc --noEmit`, Vitest, Playwright. Infrastructure: `devenv test`, `nix flake check -L`, actionlint, Hadolint, ShellCheck, Helm lint/template, kubeconform, Cosign/Syft.
- Privileged policy: deterministic tests run unprivileged; sensor/load/enforcement tests run only through `scripts/run-privileged-tests.sh` on declared root-owned VM/self-hosted runners. Ordinary local execution must report degraded/blocked instead of prompting or mutating host state.
- Evidence: `<attemptDir>/task-<N>-ebpf-runtime-security-observability.<ext>` (attemptDir = currentAttemptDir from `omo ulw-loop status --json`, `.omo/evidence/ulw/<session>/<goalId>/a<attempt>`; outside ulw-loop use `.omo/evidence/`). Every command tees stdout/stderr plus machine-readable results; benchmark tasks also retain environment manifests and raw samples.
- Numeric constants: every threshold, budget, and bound referenced by an acceptance criterion is named in a versioned JSON schema under `bench/schemas/` (for example `bench/schemas/supported-load.v1.json`, `bench/schemas/ui.v1.json`, `bench/schemas/enforcement.v1.json`, `bench/schemas/fuzz.v1.json`, `bench/schemas/compat-matrix.v1.json`, `bench/schemas/runs.v1.json`, `bench/schemas/protocol.v1.json`, `bench/schemas/rule-budget.v1.json`, `bench/schemas/metrics.v1.json`, `bench/schemas/storage.v1.json`); each schema carries an `id`/`version` pair and the tasks reference the schema path rather than hardcoding numbers inline. The schemas are the **only** source of truth for these constants; any number that is not schema-anchored is treated as a plan defect and flagged by F1's numeric-literal lint.
- Kill-switch contract: `bench/schemas/enforcement.v1.json#kill_switch_max_ms` (default `5000`, with rationale recorded in the schema's `rationale` field: "from gRPC command receipt through deny-disabled state, measured as p99 of `bench/kill-switch.sh --workloads cpu,net --pairs 10`; this is the published, source-justified bound"), `bench/schemas/enforcement.v1.json#kill_switch_benchmark_pairs` (default `10`), and `bench/schemas/enforcement.v1.json#max_recovery_ms` (default `30000` for full agent restart) are referenced by tasks 33, 34, 54, F3, and the final success criteria.
- Supported-load loss gate: zero observed critical synthetic loss only inside the published event-rate envelope from `bench/schemas/supported-load.v1.json`; deliberate saturation must show nonzero independently polled drop/lag counters and visible sequence gaps, never a false zero.
- Performance gate: randomized paired no-agent/observe/enforce runs with the workload, warmup, sample size, and confidence interval declared in `bench/schemas/runs.v1.json`; p50/p95/p99/p99.9 and throughput, CPU/RSS/event rate/loss are recorded; the upper 95% CI for p99 latency increase and for throughput decrease must each remain below 5%; an anti-limiter frozen-agent control plus identical workloads for strace/auditd/Falco are required.
- Security gate: validate SPIFFE identity/rotation, OIDC issuer/signature/audience/expiry/nonce/PKCE/device polling, RBAC negative matrix, append-only audit, policy replay/stale/disconnect, gRPC flow-control/deadline behavior, SQLCipher full-disk/WAL/integrity behavior, Kafka duplicate/retry, ClickHouse dedup/DLQ, and LSM fail-open rollback.
- Compatibility gate: the published `bench/schemas/compat-matrix.v1.json` is the expected status table for every Linux 5.15.0/6.1.0/6.6.0/`<current>` × x86_64/arm64 × BTF/LSM/cgroup/TC/runtime cell; `<current>` is the latest stable kernel pinned at plan-lock time; the acceptance test must compare actual results against that table and `current` is forbidden to drift silently between bench runs.

## Execution strategy
### Parallel execution waves
> Target 5-8 todos per wave. Fewer than 3 (except the final) means you under-split.
- **Wave 0 — Foundation (1-8):** repository/toolchain contracts, devenv+flake, preflight/evidence, generated API build, deterministic CI, and release supply chain. Task 1 blocks all work; tasks 2-8 parallelize after it where their matrix row permits (e.g., task 4 only depends on 1 and 2, so it can begin after task 2 is done; task 5 depends on only 1, so it can begin as soon as 1 is done).
- **Wave 1 — Kernel ABI and sensors (9-18):** ABI first, then independent sensor families, shared loss accounting, and attach/degrade manager. Tasks 11-17 parallelize after 9-10; task 18 integrates them.
- **Wave 2 — Node pipeline (19-26):** safe parser/bounded ingestion first, then parallel correlation/enrichment/privacy/storage/observability; standalone surfaces integrate last.
- **Wave 3 — Rules and local enforcement (27-34):** schema/compiler, predicate/sequence engines, three rule packs, then audit/enforcement lifecycle. Deny work cannot begin before audit-only behavior and node storage are proven.
- **Wave 4 — Fleet identity/control/data (35-43):** protobuf contracts first (35); SPIRE identity (36) is required before OIDC; OIDC (37) is required before PostgreSQL writes, so 36 → 37 → 38 is sequential within the wave; gRPC transport (39), Kafka (40), ClickHouse (41) chain after 38; fleet API (42) and policy rollout (43) integrate last.
- **Wave 5 — Operator and delivery (44-51):** UI foundation first; view families parallelize; CLI/systemd/OCI/Helm parallelize against stable APIs, then converge.
- **Wave 6 — Adversarial verification and release gate (52-60):** parser fuzzing, privileged loss/enforcement/compatibility, fleet security/durability, browser QA, benchmark harness, then actual comparative gate/report.
- **Final wave (F1-F4):** four independent reviewers run in parallel after all implementation tasks. All must approve; any change invalidates affected evidence and reruns the relevant reviewer.
- Execution prerequisites: load the `programming` skill before Rust/TypeScript work, `frontend` before UI implementation, `playwright` for browser tests, `visual-qa` after UI changes, and `git-master` for every Git operation/commit.
