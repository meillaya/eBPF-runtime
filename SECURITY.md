# Security policy

## Supported versions

eBPF fleet is pre-release software; there is no tagged production release
yet. Security reports are accepted against the active development line.

| Version | Supported |
| --- | --- |
| Current development line (the 0.2 fleet work, no tagged release yet) | Yes, best effort |
| Older snapshots, branches, and untagged pre-0.2 builds | No |

A fix lands on the supported development line. There is no long-term-support
branch, and older snapshots do not receive security backports. Once release
tags exist, this table will name the supported versions.

## Report a vulnerability

Use GitHub private vulnerability reporting, which opens a draft Security
Advisory:

<https://github.com/meillaya/eBPF-runtime/security/advisories/new>

Do not open a public issue, pull request, or discussion with vulnerability
details. If the private reporting form is unavailable, open a minimal public
issue that asks for a private channel and include no technical details.

Please include:

- the affected component and version or commit;
- the deployment shape (development compose, single-node tracer, Helm
  chart, or a custom deployment);
- reproduction steps or a proof of concept;
- the impact you believe the issue has;
- any suggested fix or mitigation.

## What to expect

- We aim to acknowledge a private report within 5 business days.
- We triage severity and may ask for more detail or a minimal reproducer.
- We coordinate the fix and a disclosure date with the reporter, normally
  within 90 days. The window is negotiable when a fix is already available
  or exploitation is active.
- We publish a GitHub Security Advisory and credit the reporter unless they
  ask to stay anonymous.
- This is a volunteer, early-stage project: these are goals, not a contract,
  and there is no bug bounty.

## Scope

In scope, when it has a real security impact:

- the agent: BPF loading and attach, ring-buffer decoding, the local
  SQLCipher store and its key handling, redaction, batching and outbox,
  the loopback API, and TLS client identity;
- the control plane: gRPC ingest, HTTP API, OIDC/JWT validation and role
  checks, per-node certificate identity, policy staging, commit, and
  rollout, and PostgreSQL access;
- the relay, and the Kafka and ClickHouse projections;
- the dashboard: authentication flow, session and token handling, and
  cross-site scripting or request forgery;
- the CLI (`ebpfctl`) and its credential handling;
- the build and supply chain: `bpf-build`, generated ABI code, dependency
  pinning, and the container, systemd, and Helm deployment files.

Out of scope:

- the documented development defaults: the compose development stack has
  no OIDC or TLS and binds loopback addresses, and it is not a production
  deployment;
- reports that require publishing secrets, phishing, or social engineering;
- reports that only show that published test material can be read from the
  repository. Test certificates and passwords are published on purpose; see
  the next section.

## Test-only credentials and certificates

The test keys, JWT signing material, and certificates committed under
`crates/*/tests/fixtures/` are test fixtures. The certificates and CA
material generated by `scripts/gen-test-certs.sh` are written under
`target/oidc` and used only by the local OIDC/mTLS test harness. The
passwords in `deploy/compose/` and `deploy/compose/oidc/` are development
placeholders.

This material is test-only, is published deliberately with the tests that
need it, and must never be deployed or reused. It is not a vulnerability
that a fixture key, a test certificate, or a compose development password
is known to the public. Reports that show such material being accepted by a
deployed control plane or a real node are in scope: a deployment must
require real credentials and a real CA.

## Security model and limits

These limits matter when judging a report:

- The sensors are read-only tracing programs. The project observes and
  raises alerts; it does not block syscalls or enforce policy. A deny rule
  is rejected at load time. Do not treat the agent as an enforcement
  boundary.
- Only the process and file sensors are produced. The ABI defines network,
  DNS, syscall, identity, and LSM records, but no BPF program emits them.
  Claims about network or LSM enforcement are wrong while that is true.
- The development compose stack (loopback-only, no OIDC, no TLS) is for
  evaluation. A production deployment must enable TLS/mTLS and OIDC, use
  one client certificate per node, and protect `storage.key`; see
  [the OIDC runbook](docs/runbooks/oidc-dex-ldap.md) and
  [the deployment section of the README](README.md#deployment).
- Certificate issuance and SPIRE are outside the project. The control
  plane parses a SPIFFE URI SAN from the presented certificate; it does not
  run a CA.
- The README [Limits](README.md#limits) section lists the operational gaps
  that are known and accepted.
